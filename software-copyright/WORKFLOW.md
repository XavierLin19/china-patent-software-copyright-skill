# 中国软件著作权子流程

开始前已阅读根目录 `SKILL.md` 并建立统一来源/事实登记。需要时先看 `../references/quality-gates.md`、`../references/fact-integrity.md` 和 `../templates/software-copyright/`。

## 阶段 C0：预检与真实项目识别

确认用户希望整理哪些材料：申请表辅助信息、软件说明/操作手册、代码鉴别材料、配套截图或其他文档。确认项目路径、软件全称与版本候选、著作权主体及相关时间事实（均需用户确认）、敏感/第三方代码边界、交付格式。扫描到多个项目候选时先请用户选择。

记录环境和文件读取限制。可使用脚本辅助清单、行数、哈希、格式转换和排版检查，但脚本输出只能作为证据收集；软件行业、功能、业务流程、代表性代码和操作手册结构必须基于实际阅读后判断。

## 阶段 C1：项目理解

优先阅读 README、需求/设计资料、入口、页面/路由、核心业务代码、配置与用户界面文案。发现非文本文档或无法读取格式时登记并向用户说明，不可静默遗漏。形成业务理解草稿，涵盖定位、用户、真实功能、典型流程、可观察的输入/操作/结果、证据来源及不确定项。不要把内部技术栈或推测的行业用途写成已确认产品能力。

将业务理解草稿交用户确认；未确认前不生成最终申请信息或操作手册。需要用户补充的信息以字段清单提出，不能用占位猜值替代。

## 阶段 C2：字段与代码选择

按用户目标和提交时的官方现行口径整理字段。软件全称、版本、著作权人、开发方式、发表状态/日期、权利取得方式、运行环境等事实项须明确确认或保持待填写；不要把常见默认值当作用户事实。涉及字段长度、页数或格式要求时，核实官方要求并记录核验日期；不能核验的标为待复核。

生成代码候选清单，按代表实际功能和流程的程度说明选择理由；由用户确认抽取范围。源码输出只从原项目完整选取适用代码片段/文件，逐项记录仓库相对路径、哈希（可用时）、行范围、选择理由、排除规则和是否含第三方代码。不得生成、重写或伪装代码来填页数；不得从 demo 或测试项目推断正式产品功能。

若用户需要“前/后页”式代码材料，先核实当前官方提交规则与目标模板，再依据真实页数和可用源代码处理；不要将常见规则写成无条件法律结论。版式生成后检查实际分页，不能用预估行数宣称满足页数要求。

## 阶段 C3：草稿制作

先形成可审阅草稿，再经用户确认后导出正式格式。

- **申请信息**：字段与业务理解、用户确认和来源一致；未确认项显式留空并进入 questions 清单。
- **操作手册**：以普通用户视角描述实际页面/流程、入口、可见内容、操作、约束、反馈及截图位置。章节根据真实软件组织，不套空泛固定话术，不把研发技术说明当成用户操作说明。
- **截图**：只使用项目真实界面或用户提供的截图。若无法安全运行/截图，保留清晰的待补截图标记；不得生成虚构 UI 截图。
- **代码材料**：保持源代码原样，允许为排版做有记录的分页/页眉处理；任何内容性改写须停止并征得用户确认。

分别让用户确认业务理解、申请字段、代码选择和完整草稿；用户未作出相应确认时不进入依赖该确认的下一阶段。

## 阶段 C4：格式生成与验收

使用当前可用、用户允许的文档工具生成 DOCX/PDF/TXT 等格式。不得依赖或静默安装特定商业/第三方后端；若工具不可用，交付 Markdown/TXT 草稿并说明缺少的能力，不伪称已生成文档。检查文件名、软件名称和版本一致性、真实页数、分页、页眉、代码连续性、截图占位和文档可读性。

执行 `references/quality-gates.md` 软著部分。交付申请信息草稿、业务理解、操作手册、代码来源清单及经确认的导出件；单独给出用户仍需核实/填写的官方字段。材料整理不代表已向登记机构提交或获准登记。

## 软著修订

新版本代码、名称或字段变化时创建新版本清单，重新核对相关稿件。记录输入快照与变更，不覆盖唯一原始源码或旧交付件。对旧稿中无法追溯的功能或字段，回退至项目审阅并要求确认。
