# 防止虚构技术事实

## 写作边界

1. 先写材料明确说了什么，再写解释。只有可定位材料支持的内容才可无保留地陈述为事实。
2. 推断须使用“可能”“从现有材料推测”等标记，列出前提与证据；不得为让文本完整而抹去推断标签。
3. 用户确认可以记录为 `USER_CONFIRMED`，但不能描述成被源文件独立验证。
4. 冲突时呈现来源和冲突点，并询问权威版本；不得挑选更有利的那一方。
5. 缺少数据时保留空项或写入待确认清单。不得创造实验条件、对照组、统计量、参数阈值、因果机制、性能提升或用户行为。
6. 专利范文只供学习章节功能、公开层次和一般表达动作。严禁移植范文的技术事实、公式、数字、部件关系或具有辨识度的长句。
7. 软著业务介绍不得从文件夹名、依赖名称、README 营销词或代码注释单一来源直接推断。尽量交叉核对实现、界面、需求和用户说明；边界不清就询问。
8. 代码材料保留原文，注明来源路径和版本。不得编造代码、改写源码以满足页数、把生成结果当项目已有代码。

## 冲突处理格式

```text
冲突编号：Qxxx
主题：
来源 A 与精确位置：
来源 B 与精确位置：
差异：
受影响输出：
需要用户确认的具体问题：
```

## 起草前的事实审查

逐句问：这句话是事实、推断、建议还是法律判断？它对应哪个事实 ID？来源能否定位？时效/版本是否适用？若删掉这句话，技术链或业务说明是否仍成立？若无依据，删除、降格为待确认，或向用户提问。
